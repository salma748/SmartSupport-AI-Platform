# SmartSupport AI repository analysis

## Project overview

SmartSupport AI is designed to provide e-commerce customer support through knowledge-grounded AI chat, authorized backend operations, and handoff to human agents. Customers would get policy and order answers, submit refund requests, and track support cases. Agents would handle escalations and tickets, while managers and administrators would oversee performance, knowledge, and settings. The proposed baseline covers support for a single business. Checkout, payment collection, fulfillment, and multi-tenancy are outside its scope. [Project proposal](SmartSupport%20AI-proposal.pdf) · [Functional Requirements Specification](SmartSupport_AI_Functional_Requirements_Specification.docx)

**Verified repository state.** The reviewed checkout contains a database foundation and an ASP.NET Core MVC shell. It has 26 EF Core entities, 26 entity configurations, two migrations, and a single welcome page. The business logic project is empty, and no documented customer, agent, or administrator workflow is implemented end to end.

**Review scope.** The analysis covered the first-party source, solution and project settings, migrations and model snapshot, all seven existing documentation files, and recent Git history. At the time of review, the working tree was clean on `main` at `ae6140a`, matching the locally recorded `origin/main`. Recent commits progressed from scaffolding (`217af92`) to the entity set (`ef0bb9f`), initial migration (`37b30d3`), and full relational configuration (`ae6140a`). The remote was not queried. Build success, startup behavior, migration execution, live database state, and deployment remain unverified.

## Architecture overview and repository structure

The compile-time dependencies are **PL → BLL → DAL**, with an additional **PL → DAL** reference. At runtime, `Program.cs` is the composition root and registers `SmartSupportDbContext` with SQL Server. The only controller action returns a Razor view without calling a service or querying the context. The direct PL-to-DAL reference serves startup wiring, and Razor also imports the DAL entity namespace. There is no implemented request path through the BLL. ## Database architecture

The following describes the **checked-in model and migration definitions**. The database currently deployed, if any, remains unverified. [DbContext](../src/SmartSupport-AI.DAL/Contexts/SmartSupportDbContext.cs) · [Model snapshot](../src/SmartSupport-AI.DAL/Migrations/SmartSupportDbContextModelSnapshot.cs)

| Area | Relationships and modeled data |
|---|---|
| **Users and audit — 5 tables** | `User` can have one `Customer`, one `SupportAgent`, and one `Administrator` profile through separate unique `UserId` foreign keys. Each profile has its own primary key. `ActionLog` can reference a user, conversation, and ticket independently. |
| **Conversations — 4 tables** | `Conversation` requires a customer and AI configuration. It owns ordered `Message` rows, each with optional customer and agent sender references. `Attachment` requires an uploader and at least one message or ticket reference. `CustomerFeedback` requires a conversation and customer, with an optional AI response and a rating from 1 to 5. |
| **AI and knowledge — 9 tables** | `AIResponse` references a unique output message, a triggering message, an intent, and an AI configuration. `ToolExecution` belongs to an AI response. `ResponseArticle` joins responses to articles with a composite key and stores relevance, rank, and usage. Articles reference categories and administrators. Administrators also author configurations and update system policies. Metrics may reference an agent, an AI configuration, both, or neither. |
| **Tickets — 4 tables** | `SupportTicket` references a conversation and customer. `TicketAssignment`, `TicketStatusHistory`, and `InternalNote` reference the ticket. Assignments and notes reference agents, and status history identifies the acting user. |
| **Orders and refunds — 4 tables** | `Order` belongs to a customer and has a unique order number. `OrderStatusCheck` and `RefundRequest` each reference an order and conversation, with an optional tool execution. `RefundStatusHistory` belongs to the refund request. |

- **`20261110215156_InitialCreate`** creates all 26 tables and their primary keys, including the composite `ResponseArticles` key. It contains no foreign keys, explicit secondary indexes, or check constraints. [Initial migration](../src/SmartSupport-AI.DAL/Migrations/20261110215156_InitialCreate.cs)
- **`20261113011155_CompleteEntityConfigurations`** changes six indexed string columns to `nvarchar(256)` and adds 46 foreign keys, 51 indexes including 11 unique indexes, and two check constraints. Unique indexes cover email, order number, configuration version, intent/category/policy names, the three profile links, the AI output message, and `(ConversationId, SequenceNo)`. The two checks enforce the rating range and attachment parent rule. The latest migration designer and snapshot have identical model bodies. [Second migration](../src/SmartSupport-AI.DAL/Migrations/20261113011155_CompleteEntityConfigurations.cs) · [Latest migration designer](../src/SmartSupport-AI.DAL/Migrations/20261113011155_CompleteEntityConfigurations.Designer.cs)
- **Delete behavior** is explicit. Of 46 foreign keys, 32 use `NoAction`, 11 cascade, and three set the foreign key to null. Deleting an output message cascades to its AI response, while the trigger-message reference uses `NoAction`. Removing a tool execution can clear its link from order checks and refunds. Removing an order can cascade through refund requests to their status histories. [Message configuration](../src/SmartSupport-AI.DAL/Configurations/Conversations/MessageConfiguration.cs) · [Second migration](../src/SmartSupport-AI.DAL/Migrations/20261113011155_CompleteEntityConfigurations.cs)

## Code quality and technical risks

| Finding | Consequence |
|---|---|
| **Startup and error routes are incomplete.** `DefaultConnection` is required before startup completes. Production exception handling targets `/Home/Error`, but the controller only defines `Index`. The layout also retains two links to the removed Privacy action. | A fresh checkout needs external configuration even for the welcome page. The configured production error destination and Privacy links have no corresponding action in the checkout. | **The second migration assumes compatible existing data.** It adds constraints and reduces column lengths without data cleanup or backfill. | If anyone populated a database under `InitialCreate`, duplicate values, orphaned references, oversized values, or rows that fail the new checks could block the upgrade. Whether such a database exists is unknown. [Second migration](../src/SmartSupport-AI.DAL/Migrations/20261113011155_CompleteEntityConfigurations.cs) |
| **Foreign keys enforce existence independently.** A ticket’s `CustomerId` can differ from its conversation’s customer. Similar consistency gaps exist across feedback, order operations, and AI response messages. `SenderType`, `User.Role`, and lifecycle states are strings without corresponding database rules. | The application will need explicit ownership, sender, and state-transition enforcement. The unique message sequence index protects ordering within a conversation, but there is no client message key for duplicate submission handling. | **Concurrency and financial invariants have no implementation.** `IsCurrent` has no filtered unique index, and there is no ticket concurrency token. `RefundRequest` lacks a durable operation key, currency, confirmation or approval record, and provider reference. | The current design provides no guarantee of one current assignment or one refund per operation. ## Documentation inconsistencies

- **The three-project solution covers only part of the planned architecture and first milestone.** The plan calls for Web, Services, AI, and Data boundaries. The 13 November Sprint 1 gate includes Identity, repositories and transaction boundaries, and chat grounded in published knowledge. The checkout provides the MVC and database foundation. Work in progress outside the checkout and milestone completion remain unverified. [Project plan, pp. 2–3](Project_Plan_and_NFRs.pdf) · [Functional Requirements Specification, § 10](SmartSupport_AI_Functional_Requirements_Specification.docx)
- **The relational mapping broadly matches the second migration.** The mapping flags inconsistent counts in its source design. Its 43 conceptual relationships can be reconciled with 46 physical foreign keys by expanding the single subtype relationship into three links and the retrieval relationship into two junction links. Its “circular FK path” heading is misleading for the checked-in schema. The attachment links converge on a dependent table and do not form a foreign-key cycle. [Relational mapping](Database/Relational_Mapping.md) · [Second migration](../src/SmartSupport-AI.DAL/Migrations/20261113011155_CompleteEntityConfigurations.cs)
- **Scope and release language differ across documents.** The plan lists automatic language detection as Could and also includes it in the usability NFR. It lists PII masking as Should and also specifies it as a privacy requirement. The proposal makes Azure services conditional on availability and cost, while the dated plan makes Azure deployment a Must. The task assignment describes a suggested six-to-eight-week sequence, while the dated plan uses four overlapping November sprints. The FRS records some of these conflicts and remains proposed for approval. It also refers to `SmartSupport_AI_Project_Plan_and_NFRs.pdf`, which is tracked as `Project_Plan_and_NFRs.pdf`. ## Recommended development priorities

1. **Make the foundation reproducible.** Document required configuration, verify both a clean SQL Server install and an upgrade from `InitialCreate`, restore usable error handling, and establish a build and test pipeline. Confirm the Identity data model before adding users or exposing customer data.
2. **Deliver one authenticated support flow end to end.** Establish the BLL service and transaction boundaries, persist an owned conversation and its messages, retrieve published knowledge, show article references, and support ticket creation when AI is unavailable. Test denied access and provider failure alongside the success path.
3. **Add controlled order tools and human handoff.** Start with read-only order lookup. Define durable operation records, confirmation, approvals, and reconciliation before enabling refunds. Implement atomic agent claims, ticket transitions, and authorized live updates before adding broader agent workspace features.
4. **Validate release and operational requirements.** Use the FRS scenarios to verify the agreed Must scope, then exercise reporting fixtures, privacy and retention behavior, deployment, and performance under defined workloads. Resolve optional scope against the agreed delivery dates.
